## Q-1. Область покрытия: «полка» vs «применяемый код»

Проверено грепом по всему `src` (исключая сам `shared/engines/`):

| Модуль | Кто его использует в этом дереве |
|---|---|
| `shared/engines/kinetic/**` (весь фасад `useKineticValue`, 1 300+ строк вместе с форками) | **никто**; доступен только через реэкспорт `shared/index.ts` |
| `shared/engines/gesture/inertia/releaseKinetics.ts` (`resolveReleaseKinetics`, `projectMomentum`, `MOMENTUM_DEFAULTS`) | **никто** |
| `shared/engines/motion/compositor/compositedRide.ts` (`useCompositedRide`, `createCompositedRide`, `flyTo`, `dragBinding`) | **никто** (карусель собирает тот же путь из примитивов в `useTrackBinding`) |
| `shared/clientState/media/library/**` (`useBreakpoint`, `useShortLandscape`, `useOrientation`) | **никто** (приложение и компонент ходят через `useMedia`) |
| `shared/clientState/environment/library/**` | **никто** (используется форк `useUserEnvironment/internal/**`) |
| `shared/theme/**` | приложение-стенд (`main.tsx`, `App.tsx`) |
| `shared/engines/kinetic/internal/**` | только внутри `kinetic` |

Это ровно та ситуация, про которую в памяти записано «shared — общая
библиотека, не судить по нуждам карусели». Но для карты рисков мне нужен
твой критерий:

**Вопрос:** какой из вариантов?

- **(a)** Полка тестируется как публичная библиотека: неиспользуемый в этом
  дереве код (kinetic, releaseKinetics, compositedRide, library-копии) имеет
  такие же права на покрытие, как и применяемый.
- **(b)** Полка тестируется, но по остаточному принципу: сначала риски
  применяемого пути, неиспользуемое — только там, где поломка не всплывёт
  вообще ничем.
- **(c)** В этом прогоне ограничиваемся тем, что реально исполняется
  каруселью и стендом; полка вне зоны — отдельной задачей.

### ✅ ОТВЕТ: вариант (a) — полка входит в зону покрытия

Неиспользуемый в этом дереве код полки (`kinetic`, `releaseKinetics`,
`compositedRide`, `library`-копии) имеет те же права на покрытие, что и
применяемый. С уточнением: **раз там в основном форки, тесты тоже будут
форкнутыми** — копия теста с минимальными правками, а не написанный заново
набор.

Следствия для Этапов 3–5:
* риски для форкнутого кода формулируются один раз, а тест под них
  тиражируется по копиям;
* «тест существует только у оригинала» — это пробел, а не экономия.

## Q-2. Идентичные форки: считать ли покрытие одного покрытием другого

Дифом установлено: `kinetic/internal/gesture/**` и `kinetic/internal/motion/**`
**побайтово совпадают по коду** с `shared/engines/gesture/**` и
`shared/engines/motion/**` (кроме урезанного `compositedRide.ts` и двух
`index.ts`); расхождения — только в тексте комментариев.

При этом это **разные модули с разным состоянием**: у форков собственные
модульные синглтоны, собственный кэш `isWaapiSupported`, собственные Map-ы.

**Вопрос:** для идентичного по коду форка достаточно ли
portability-теста (что модуль не импортирует ничего снаружи себя + собирается),
или каждый форк должен иметь собственный поведенческий тест того же
инварианта?

### ✅ ОТВЕТ: поведенческий тест форкается; portability-тесты не нужны

1. Идентичность кода **не** заменяет тест: у каждого форка свой поведенческий
   тест того же инварианта (форкнутая копия, минимальные правки) — см. ответ
   на Q-1.
2. **Portability-тесты не нужны.** Задачи защищать полку от недокопирования
   или перекопирования нет.

Следствие для Этапа 4: в корзину DELETE заранее попадают тесты, чей
единственный смысл — сторожить границы копирования, а не поведение. По
инвентаризации Этапа 2 это как минимум:

* `shared/engines/gesture/tests/portability.test.ts`
* `shared/engines/motion/tests/portability.test.ts`
* `shared/engines/kinetic/tests/portability.test.ts`

и, вероятно, того же рода `shared/viewportObservation/tests/singleSource.test.ts`
и `shared/clientState/shared/tests/singleStore.test.ts` — по ним вынесу
вердикт после чтения их тел на Этапе 2, а не по названиям.

## Q-3. `boundary/` — слой или только тесты

`src/components/Carousel/boundary/` содержит **только** `README.md` и `tests/`
(`boundaries.test.ts`, `slide-contract.test.ts`). Продакшн-кода там нет.
README описывает эту папку как «нейтральную территорию над двумя половинами»
(`client/` и `data-gen/`) с архитектурными тестами шва.

Это единственное место в дереве, где `tests/` не соседствует с кодом того же
каталога, — то есть формально соглашение «тесты лежат в `test/` своего
каталога» выдержано (каталог `boundary` существует), но каталог существует
**ради** тестов.

**Вопрос:** это осознанная конструкция, которую надо сохранить как есть, или
шов `client ↔ data-gen` должен проверяться откуда-то ещё?

## Q-4. Что считать «продуктовым контрактом» карусели

Для Этапа 3 нужен внешний критерий «что компонент обещает наружу». Из кода
однозначно читается только техническая поверхность (`CarouselProps`,
`CarouselHandle`, `CarouselStatusSnapshot`, четыре слота, `className`-мапа,
CSS-переменные). Поведенческие обещания — «клик всегда доезжает до границы
страницы», «поворот экрана не сбрасывает позицию просмотра», «жест
перехватывает летящую ленту» — выведены мной из кода как **описание
реализации**, а не как заявленный контракт.

**Вопрос:** есть ли список поведенческих обещаний, который считается
контрактом (то, что нельзя сломать), или его надо вывести из кода и утвердить
вместе с картой рисков на Этапе 3?

Без ответа я на Этапе 3 выведу его из кода и вынесу отдельным разделом в
`TEST-RISKS.md` на твоё утверждение — но тогда это будет мой вывод, а не твой
контракт.

# context — правила и инструменты для нового проекта

Полка не с кодом, а с **порядком работы**. Всё, что здесь лежит, добыто на
реальном проекте задним числом: база знаний и правила качества собирались уже по
готовому коду, и это оказалось на порядок дороже, чем вести их с самого начала.
Полка существует, чтобы следующий проект начинался сразу с этого состояния.

Отсюда её единственное правило: **сажается в проект до первой строчки кода, а не
после.**

## Что внутри

| Файл | О чём |
| --- | --- |
| [`quality.md`](./quality.md) | **планка качества**: `enterprise / senior++` целиком и безусловно, по всем общепринятым критериям, **плюс** конкретные симптомы, которые видно в диффе — от границ слоёв до формы одной функции. Там же признаки эталонного узла и раздел «что дефектом НЕ является» |
| [`workflow.md`](./workflow.md) | петля работы, **обязательная сверка качества**, правила коммитов, форма отчёта |
| [`knowledge-base.md`](./knowledge-base.md) | как устроена база знаний, что в неё пишут, что проверяется машиной, и почему она ведётся параллельно коду |
| [`CLAUDE.template.md`](./CLAUDE.template.md) | шаблон правил проекта: постоянное уже написано, проектное помечено `<...>` |
| [`tools/graph.mjs`](./tools/graph.mjs) | счётный инструмент: **досье на адрес** (`brief`), циклы импортов, радиус поражения, мёртвые экспорты, объёмы, сводка открытого и **сверка базы с кодом** |
| [`environment.md`](./environment.md) | **среда**: что вызывает запрос подтверждения, что снимается списком разрешений, а что нет, и раздел труда между оболочкой и инструментами. Ставится, чтобы задачу можно было поставить и отойти |
| [`settings.template.json`](./settings.template.json) | список разрешений, который кладут в новый проект как `.claude/settings.json` |
| [`stryker.template.json`](./stryker.template.json) | скелет мутационного прогона: три настройки, добытые замером, и правило отбора области. Заполняется `mutate` под свой проект |

Чего здесь нет намеренно: эталонных узлов. Их нельзя привезти с собой — в новом
проекте их ещё не существует. Привезены **критерии**, по которым их потом
отбирают (`quality.md`, раздел «Эталонный узел»).

## Как посадить в новый проект

1. Скопировать эту папку в новый проект.
2. Завести папку базы (например `.context/`) и положить в неё
   `tools/graph.mjs` — это рабочая копия инструмента.
3. Открыть в нём блок `CONFIG` в самом верху — **это единственное место, где
   задаются пути и имена.** Поправить `src` под структуру проекта; остальное
   менять только если файлы базы называются иначе. `toolCopy` оставить, если
   полка правил едет вместе с проектом, иначе поставить `null`.
4. Скопировать `CLAUDE.template.md` в корень проекта как `CLAUDE.md` и заполнить
   `<...>`: чем является проект, устройство, публичная поверхность, команды
   проверок, пути к базе.
5. Завести файлы базы по таблице из
   [`knowledge-base.md`](./knowledge-base.md). **Проверено пересадкой в пустой
   проект — без этих трёх `verify` краснеет сразу:**
   - `00-map.md` — и в нём сразу назван каждый файл кода, какой уже есть;
   - `01-facts.md` — **с таблицей машинных сверок**, скопированной из
     `knowledge-base.md`: её отсутствие ловит проверка «полка правил не
     отстаёт», а не «забыли раздел»;
   - `02-todo.md` — **создать пустым**, иначе проверка отложенного сообщает,
     что файла нет.

   Остальные (`07-invariants.md`, `08-tests.md`, `09-decisions.md` и прочие)
   заводятся, когда в них появляется содержимое: пока в коде нет ни одной
   пометки, их отсутствие проверку не трогает.
6. Прогнать `node <база>/graph.mjs verify`. **Зелёным он станет не «сам собой»,
   а когда карта назовёт первые файлы** — и это первая полезная работа, а не
   препятствие: правило «база описывает код целиком» начинает действовать с
   первой строчки, а не с того дня, когда кто-то решит его включить. Дальше
   каждое покраснение означает ровно одно: база отстала от кода.
7. Посадить **среду** по [`environment.md`](./environment.md): создать
   `.claude/` и положить туда `settings.template.json` как `settings.json`,
   поправив в нём пути и команды под проект; там же — `.gitattributes` с
   политикой концов строк, и его заводят **до первого коммита**. Шаг стоит
   последним по порядку, но не по важности: без него первая же длинная задача
   встанет на запросе подтверждения и будет ждать человека, который отошёл, а
   правки на машине с CRLF начнут молча не применяться.
8. Когда появятся первые тесты — положить `stryker.template.json` как
   `stryker.config.json` и заполнить в нём `mutate`. До первых тестов он
   бесполезен, поэтому шаг и стоит отдельно.

Дальше можно писать код. Правила уже действуют: качество сверяется по
`quality.md`, работа идёт по петле из `workflow.md`, база наполняется вместе с
кодом.

## Почему именно так

Три вещи, ради которых всё это заведено. Каждая стоила отдельного разбора:

- **Правило без проверки гниёт молча.** Договорённость в README не держит ничего:
  её нарушают не по злому умыслу, а потому что не прочли. Поэтому всё, что можно
  посчитать, считает инструмент, а текст только объясняет причину.
- **Найденный дефект чинится, а не описывается.** Место, куда можно положить
  известный дефект, рано или поздно им наполняется, а документация об опасном
  коде делает опасный код разрешённым.
- **Базу дешевле вести, чем восстанавливать.** В момент написания причина решения
  ещё известна. Через месяц её придётся выводить из кода, и часть выведется
  неверно — причём незаметно.

# context — правила и инструменты для нового проекта

Полка не с кодом, а с **порядком работы**. Всё, что здесь лежит, добыто на
реальном проекте задним числом: база знаний и правила качества собирались уже по
готовому коду, и это оказалось на порядок дороже, чем вести их с самого начала.
Полка существует, чтобы следующий проект начинался сразу с этого состояния.

Отсюда её единственное правило: **сажается в проект до первой строчки кода, а не
после.**

## Что внутри

| Файл | О чём |
| --- | --- |
| [`quality.md`](./quality.md) | **планка качества**: `enterprise / senior++` целиком и безусловно, по всем общепринятым критериям, **плюс** конкретные симптомы, которые видно в диффе — от границ слоёв до формы одной функции. Там же признаки эталонного узла и раздел «что дефектом НЕ является» |
| [`workflow.md`](./workflow.md) | петля работы, **обязательная сверка качества**, правила коммитов, форма отчёта |
| [`knowledge-base.md`](./knowledge-base.md) | как устроена база знаний, что в неё пишут, что проверяется машиной, и почему она ведётся параллельно коду |
| [`documentation.md`](./documentation.md) | документация **для человека** и комментарии в коде: пять видов документов и границы между ними, витрина возможностей, когда документ заводят и удаляют, правила комментариев и крючки, которыми всё это держится |
| [`CLAUDE.template.md`](./CLAUDE.template.md) | шаблон правил проекта: постоянное уже написано, проектное помечено `<...>` |
| [`tools/graph.mjs`](./tools/graph.mjs) | счётный инструмент: **досье на адрес** (`brief`), циклы импортов, радиус поражения, мёртвые экспорты, объёмы, сводка открытого и **сверка базы с кодом** |
| [`tools/graph.md`](./tools/graph.md) | справочник его режимов: что делает каждый и **чего не делает**. Без него инструмент приезжает набором команд без границ применимости |
| [`environment.md`](./environment.md) | **среда**: что вызывает запрос подтверждения, что снимается списком разрешений, а что нет, и раздел труда между оболочкой и инструментами. Ставится, чтобы задачу можно было поставить и отойти |
| [`settings.template.json`](./settings.template.json) | список разрешений, который кладут в новый проект как `.claude/settings.json` |
| [`stryker.template.json`](./stryker.template.json) | скелет мутационного прогона: три настройки, добытые замером, и правило отбора области. Заполняется `mutate` под свой проект |
| [`task.skill.template.md`](./task.skill.template.md) | скилл «начать задачу с правильного яруса входа»: кладётся в `.claude/skills/task/SKILL.md` и правится под пути проекта. Исполняет соразмерность вместо того, чтобы каждая сессия выводила её из правил заново |
| [`probe.skill.template.md`](./probe.skill.template.md) | скилл «прогон проб 7×7»: определения пробы, раунда и прогона, оси, по которым пробы выбираются, норма фальсификаций, гигиена отката. Заменяет пересказ задачи каждый раз заново |
| [`audit.skill.template.md`](./audit.skill.template.md) | скилл «сверка готовности обвязки»: что мерить, шесть разделов с весами, петля улучшений, форма отчёта. Опирается на файл памяти в базе — прошлые оценки и реестр отклонённого |

Чего здесь нет намеренно: эталонных узлов. Их нельзя привезти с собой — в новом
проекте их ещё не существует. Привезены **критерии**, по которым их потом
отбирают (`quality.md`, раздел «Эталонный узел»).

## Как посадить в новый проект

Порядок проверен пересадкой в пустой проект: пройденный до конца, он даёт
`verify` с кодом возврата 0. Занимает минут десять, `node` — единственное, что
нужно из инструментов.

**Что должно получиться в корне проекта:**

```
<корень>/
  CLAUDE.md                  ← из CLAUDE.template.md, заполнить <...>
  .gitattributes             ← из environment.md, до первого коммита
  .nvmrc                     ← версия среды, шаг 4-бис
  package.json               ← там же появляется команда `check` и `engines`
  .claude/
    settings.json            ← из settings.template.json
    skills/
      task/SKILL.md          ← из task.skill.template.md
      probe/SKILL.md         ← из probe.skill.template.md
      audit/SKILL.md         ← из audit.skill.template.md
  .context/                  ← папка базы (имя ваше, но дальше примеры с ней)
    graph.mjs                ← рабочая копия tools/graph.mjs
    graph.md                 ← его справочник, из tools/graph.md
    00-map.md
    01-facts.md
    02-todo.md
  src/shared/context/        ← эта папка целиком, если едет с проектом
```

Появляются позже и в дерево не входят: `stryker.config.json` — с первыми
тестами (шаг 8), `.context/11-readiness.md` — с первой сверкой готовности.

### Шаг 1. Положить файлы

Скопировать **эту папку** в проект (например в `src/shared/context/`), затем
разложить из неё по этой таблице (числа здесь нет намеренно: строк прибавлялось,
и счёт за ними не поспевал):

| Откуда | Куда | Что потом сделать |
| --- | --- | --- |
| `tools/graph.mjs` | `.context/graph.mjs` | поправить `CONFIG`, шаг 2 |
| `tools/graph.md` | `.context/graph.md` | ничего: справочник режимов, едет как есть |
| `CLAUDE.template.md` | `CLAUDE.md` в корне | заполнить `<...>`, шаг 3 |
| `settings.template.json` | `.claude/settings.json` | сверить команды, шаг 5 |
| блок `.gitattributes` из `environment.md` | `.gitattributes` в корне | ничего, но **до первого коммита** |

### Шаг 2. Поправить `CONFIG` в `.context/graph.mjs`

Блок `CONFIG` в самом верху файла — **единственное место, где задаются пути и
имена.** Обычно трогают эти:

- `src` — путь к исходникам относительно папки базы (по умолчанию `"../src"`);
- `toolCopy` — путь к копии инструмента на полке; если полка с проектом не
  едет, поставить `null`;
- `rulesManifest.rules` — **список файлов правил**. У нового проекта он один:
  `"../CLAUDE.md"`. Вложенные `CLAUDE.md` в папках заводят позже, по мере того
  как появляются правила, действующие только там, — и тогда же дописывают сюда.
  Заявленный, но отсутствующий файл роняет прогон намеренно: это значит, что
  файл правил потеряли.

**После правки `CONFIG` — скопировать рабочий файл обратно на полку.** Сверка
требует побайтового совпадения копий, а `CONFIG` вы только что изменили: без
этого шага первый же `verify` скажет «копия разошлась». Полочная копия — не
музейный образец, а зеркало рабочего файла, и в ней живёт `CONFIG` **вашего**
проекта. Проверено пересадкой: без этой строки посадка краснеет на ровном месте.

Остальное трогают, только если файлы базы называются иначе, чем в примерах. С
одной оговоркой, стоившей красного прогона на пробе: **в `docPathExceptions`
удаляют только строки, помеченные проектными.** Помеченные полочными описывают
файлы самой полки и приезжают вместе с ними; вычистив список целиком, вы
получите красный первый `verify` на тексте, который сами же и привезли.

### Шаг 3. Заполнить `CLAUDE.md`

В шаблоне размечены места `<...>`: чем является проект, его устройство,
публичная поверхность, команды проверок, пути к базе. Всё остальное в нём уже
написано и переписывания не требует.

### Шаг 4. Завести три файла базы

Именно три — без них `verify` краснеет сразу, и это проверено, а не
предположено:

| Файл | Что в нём должно быть с первого дня |
| --- | --- |
| `00-map.md` | назван **каждый** файл кода, какой уже есть в проекте |
| `01-facts.md` | **три таблицы из `knowledge-base.md`, скопированные целиком, как есть**: «Скилл / Шаблон на полке» (пустая, строки появятся с первым скиллом), «Раздел правил проекта / Где на полке» и «Что сверяется / Как». На каждую опирается своя сверка |
| `02-todo.md` | можно пустым, но файл должен существовать |

Остальные (`07-invariants.md`, `08-tests.md`, `09-decisions.md` и прочие)
заводят, когда в них появится содержимое: пока в коде нет ни одной пометки, их
отсутствие проверку не трогает.

### Шаг 4-бис. Завести одну команду проверок и закрепить версию

Две строки в манифесте проекта, обе окупаются в первый же день:

- **`check`** — цепочка из всего обязательного набора: типы, линт, формат,
  тесты, сверка базы. Отдельные вызовы держатся памятью и порядком, один — нет,
  и он же останавливается на первом красном. Заведя команду, **допишите её в
  список разрешений** — иначе первый же прогон встанет на подтверждении. Сборку и браузерный смоук в
  цепочку не кладут: первая обычно дублирует проверку типов, второй гоняется по
  требованию.
- **версия среды** — `engines` плюс файл версии (`.nvmrc`). Полка обещает
  переезд на новую машину; без закреплённой версии расхождение вылезет не
  ошибкой установки, а другими числами прогона, и виноватым будет «непонятно
  кто».

### Шаг 5. Сверить команды в `.claude/settings.json`

В списке разрешений перечислены команды проверок (`npm run typecheck`, `npm
test` и прочие) и путь `node .context/graph.mjs *`. Если у проекта другой
менеджер пакетов, другие имена скриптов или другая папка базы — поправить строки
под себя. Пропущенная строка означает запрос подтверждения посреди работы, и
всплывёт он тогда, когда человек уже отошёл.

### Шаг 6. Прогнать проверку

```
node .context/graph.mjs verify
```

Код возврата 0 — **база и правила встали**; посадка на этом не закончена,
остаются скиллы (шаг 7). Если красный, смотреть таблицу ниже: почти все причины —
это шаг 4, сделанный не до конца.

| Что говорит | Что это значит |
| --- | --- |
| `Покрытие карты … не упомянуто: N` | в `00-map.md` не назван файл кода. Назвать — это и есть первая полезная работа: правило «база описывает код целиком» начинает действовать с первой строчки, а не с того дня, когда кто-то решит его включить |
| `Полка правил не отстаёт … таблицу сверок не нашли` | в `01-facts.md` нет таблицы «Что сверяется / Как» |
| `Разделы правил … таблицу разделов не нашли` | в `01-facts.md` нет таблицы «Раздел правил проекта / Где на полке» |
| `Скиллы проекта … таблицу скиллов не нашли` | в `01-facts.md` нет таблицы «Скилл / Шаблон на полке» — её копируют пустой, с одной шапкой |
| `Разделы правил … не классифицирован: X` | в `CLAUDE.md` появился раздел `X`, а строки про него в таблице нет: решить, едет он на полку или проектный, и дописать |
| `Отложенное … файла нет: 02-todo.md` | файл не создан |

Дальше каждое покраснение означает ровно одно: **база отстала от кода.**

### Шаг 7. Скиллы

Шаблоны кладутся в `.claude/skills/<имя>/SKILL.md`:

| Шаблон | Куда | Зачем |
| --- | --- | --- |
| `task.skill.template.md` | `skills/task/SKILL.md` | ярусный вход в задачу; без него соразмерность каждый раз выводится из правил заново |
| `probe.skill.template.md` | `skills/probe/SKILL.md` | прогон проб по обвязке: «прогон 7×7» вместо пересказа условий каждый раз |
| `audit.skill.template.md` | `skills/audit/SKILL.md` | сверка готовности обвязки с оценкой и планом |

Пути внутри поправить под проект — **а затем скопировать файл обратно на
полку**, как и инструмент: сверка требует побайтового совпадения. Отсюда правило
для текста скилла: **пути — проектные, слова — нейтральные.** Название своего
продукта в описание не вписывать; оно уедет в следующий проект и будет там
врать. Поймано пробой: в описании стояло имя продукта.

Скиллу `audit` нужен ещё файл памяти в базе — прошлые оценки и **реестр
отклонённого**. Он заводится при первой сверке; до неё его отсутствие ничему не
мешает, а вот без него вторая сверка предложит то, от чего уже отказались.

Заодно объявить состав: строка на каждый скилл в таблице «Скилл / Шаблон на
полке» в `01-facts.md` — её сверяет `verify` трижды. И помнить, что **новый
скилл текущая сессия не увидит**: перечень собирается на старте, нужен
перезапуск. Подробности — в [`environment.md`](./environment.md).

**На этом посадка закончена — дальше можно писать код.** Правила уже действуют:
качество сверяется по `quality.md`, работа идёт по петле из `workflow.md`, база
наполняется вместе с кодом.

### Шаг 8. Уже по ходу работы, когда появятся первые тесты

Единственный шаг, который делают **не при посадке**: положить
`stryker.template.json` как `stryker.config.json` в корень и заполнить в нём
`mutate` — область прогона. До первых тестов он бесполезен, поэтому и стоит
после черты, а не в ряду остальных.

## Почему именно так

То, ради чего всё это заведено. Каждое стоило отдельного разбора:

- **Правило без проверки гниёт молча.** Договорённость в README не держит ничего:
  её нарушают не по злому умыслу, а потому что не прочли. Поэтому всё, что можно
  посчитать, считает инструмент, а текст только объясняет причину.
- **Найденный дефект чинится, а не описывается.** Место, куда можно положить
  известный дефект, рано или поздно им наполняется, а документация об опасном
  коде делает опасный код разрешённым.
- **Базу дешевле вести, чем восстанавливать.** В момент написания причина решения
  ещё известна. Через месяц её придётся выводить из кода, и часть выведется
  неверно — причём незаметно.

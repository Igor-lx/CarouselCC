# environment — чтобы задача не вставала на подтверждениях

Правила и инструменты переносятся копированием папки, а вот **среда — нет**: в
новом проекте нет ни списка разрешений, ни знания о том, какие команды его
обходят. Разница видна сразу: поставил задачу, отошёл — и вернулся к
запросу подтверждения, который стоит там с первой минуты. Этот файл существует,
чтобы такого не было ни в одном новом проекте.

Всё ниже — не рассуждение, а наблюдения, снятые на живой сессии. Где механизм
не установлен, так и написано.

## Что снимается списком разрешений

Рядом лежит [`settings.template.json`](./settings.template.json) — его кладут в
новый проект как `.claude/settings.json`. Список закрывает две группы:

- **команды проверок и работы:** `npm run …`, `npx vitest|eslint|tsc|prettier`,
  `npx stryker run`, `node .context/graph.mjs …`;
- **чтение названного файла:** `cat`, `head`, `tail`, `sed -n`, `wc`, `diff`,
  `od`, `ls`, а также `grep` по конкретному пути.

Записи сверяются по началу команды. Склейка через `&&` разрешения **не
наследует**: разрешённой должна быть каждая часть, поэтому `cd` в списке стоит
отдельно — без него любая команда вида `cd проект && npm test` будет спрашивать.

## Что списком НЕ снимается

**Обход дерева каталогов через оболочку спрашивает всегда.** Проверено прямым
опытом: `grep -n "…" src/app/App.tsx` проходит молча, а
`grep -rn "…" src/components/…/docs` требует подтверждения — и требует его даже
после того, как `Bash(grep *)` добавлен в список. То же ожидаемо для `find` по
дереву.

Механизм из сессии не виден, и выдавать догадку за факт тут нельзя. Наблюдаемое
правило простое и этого достаточно: **названный файл — проходит, обход дерева —
спрашивает.**

**Догадка о механизме здесь была и оказалась неверной — она стоит того, чтобы
её помнить.** Записанным ранее объяснением было «склейка из трёх и более команд
и редиректы»; на следующем же сеансе замер его опроверг напрямую. Прошли молча:
конвейер с редиректом (`… 2>&1 | grep …`), редирект в файл вместе с `;` и второй
командой, склейка из семи частей с `&&`. Спросил при этом единственный вызов, у
которого не было ни одного из названных признаков, — **`grep` с многословным
образцом по одному названному файлу**.

Отсюда два вывода, и первый важнее второго:

- **Мы не знаем, что именно спрашивает,** и любая следующая формулировка
  механизма будет такой же догадкой. Записывать её как факт нельзя: правило,
  выведенное из четырёх наблюдений, ломается на пятом — и тогда ему перестают
  верить целиком.
- **Обход есть, и он не требует знания механизма: поиск идёт инструментом
  Grep — всегда.** Не «когда обход дерева», не «когда файл не назван», а всегда,
  включая поиск по одному конкретному файлу. Этот инструмент не спрашивает
  никогда, и именно это свойство, а не догадка о причине, снимает вопрос.

За Bash остаётся то, где он незаменим: запуск команд и фильтрация **их вывода**
трубой. Поиск по файлам репозитория — не его работа.

**Отсюда белый список запуска вместо списка запретов.** Через оболочку идёт
только то, что показало себя устойчиво разрешённым: проверки проекта (`npm …`),
инструмент базы (`node <база>/graph.mjs …`), форматирование и мутации (`npx …`),
разовый скрипт (`node <файл.mjs>`), копирование при синхронизации полки (`cp`) и
чтение состояния репозитория для отчёта (`git status`, `git log`, `git diff`).

**Всё остальное — инструментами:** чтение `Read`, поиск `Grep`, перечисление
`Glob`, правка `Edit`/`Write`. В «остальное» попадают и команды, которые в списке
разрешений **стоят** и всё равно однажды спросили: `grep`, `head`, `diff`,
`find`, `sed`, `mv`, `printf`. Нужно сравнить два файла — читать оба или писать
разовый скрипт, а не звать `diff`.

Список запретов пробовался дважды и оба раза разошёлся с наблюдением в тот же
день. Белый список этим не страдает: он не объясняет причину, он её обходит.

## Отсюда раздел труда, а не отказ от Bash

| Задача | Чем |
| --- | --- |
| Запуск: обязательный набор одной командой, сборка, инструмент базы, `git status/log/diff` | Bash |
| Чтение любого файла | **только Read** |
| Поиск по репозиторию и по одному файлу | **инструмент Grep** — подтверждений не требует в принципе |
| Перечисление файлов по маске | **инструмент Glob** |
| Правка и создание файлов | **Edit / Write** |

Последняя строка — не вкус, а механика: `Edit` отказывается править файл,
который не был прочитан **инструментом** `Read` в этом же диалоге. Прочитал
через `cat` — на правку уйдёт лишний вызов. Так что Bash-чтение перед правкой
не экономит, а добавляет заход.

Выигрыша в скорости или в токенах у Bash-чтения нет: оболочка порождает процесс,
инструмент Grep запускает тот же поисковик напрямую, объём вывода сопоставим.
Единственная разница — где всплывает подтверждение.

## Скиллы: как они включаются и что с ними переносится

Скилл — **не пассивная надстройка**. Перечень скиллов собирается на старте
сессии, а сам скилл загружается только по вызову: вашему (`/имя`) или моему,
если описание в его шапке подходит задаче. Отсюда три вещи, каждая проверена:

- **новый скилл в текущей сессии не появится** — нужен перезапуск или очистка
  контекста; правки уже существующего файла читаются при каждом вызове;
- **описание в шапке — это и есть механизм срабатывания.** Скилл с расплывчатым
  описанием не вызовется никогда: по нему не опознать, к какой задаче он;
- **`user-invocable: true`** в шапке делает его доступным по `/`.

Раскладка на диске: `<корень>/.claude/skills/<имя>/SKILL.md`, шапка —
`name`, `description`, `user-invocable`.

**Перенос.** Скиллы едут с полкой шаблонами и раскладываются при посадке. Чтобы
они не терялись и не расходились, состав объявляется таблицей в базе, а сверка
проверяет три вещи разом: объявленный существует, существующий объявлен, шаблон
на полке совпадает с рабочим файлом байт в байт. **Агенты так проверить
нельзя** — это возможности окружения, а не файлы репозитория; их называют прозой
в разделе ниже, и актуальность держится правилом «завёл — обнови список», а не
машиной.

## Инструменты среды, которые правила обязаны назвать

Окружение обычно даёт больше, чем сборка и тесты, и это «больше» не срабатывает
само: инструмент, не названный в правилах, не существует для того, кто их
читает. Три вещи стоит назвать поимённо и **в том разделе, где они применяются**,
а не общим списком:

- **команда ревью правки** — на узел, до коммита. Зелёный набор проверок говорит
  «не сломано», а не «сделано хорошо»: он не видит ни лишней работы, ни
  разъехавшегося слоя, ни решения, принятого дважды. Самопроверка по памяти не
  видит того же — она смотрит тем же взглядом, которым писалось;
- **команда запуска приложения** — когда правка видна на экране. Ни база, ни
  тесты, ни смоук не отвечают на вопрос «как это выглядит и ощущается»;
- **агент широкого поиска** — на сметания вида «найди все места, где…», чтобы
  выдача не оседала в основном контексте. Запускается по решению разработчика,
  но **предлагается тем, кто видит форму задачи**: правило «по прямому указанию»
  без критерия перекладывает на него вопрос, на который у него нет данных —
  сколько файлов придётся пройти и нужен ли дословный текст, видно изнутри
  работы, а не со стороны. Форма опознаётся по трём условиям сразу: десятки
  файлов; на выходе нужен список или вывод, а не текст для рассуждения; где
  смотреть, заранее неизвестно. Не выполнено одно — обычный поиск дешевле.
  Второе условие важнее прочих: агент читает выдержками, поэтому область он
  **очерчивает**, а не заменяет, и его вывод подтверждается чтением названных
  им строк.

Названия у команд свои в каждом окружении; правило здесь не про названия, а про
**место**: инструмент вписывают в тот раздел, где он и нужен.

## Мелочи среды, на которых спотыкаются молча

- **Рабочая папка Bash сбрасывается между вызовами.** Сессия может стартовать
  уровнем выше проекта, и тогда `git status` отвечает `not a git repository`.
  Писать `cd <проект> && …` либо абсолютные пути, а не полагаться на то, что
  предыдущий `cd` ещё действует.
- **Труба уничтожает код возврата.** `проверка | tail` возвращает результат
  `tail`, поэтому и `&&` после неё не спасает. Проверки прогоняются своим
  вызовом, их вывод читается, и только потом делается коммит.
- **`tail` срезает начало отчёта.** У инструментов, печатающих несколько
  секций, первая — самая важная (покрытие карты). Смотреть `head`, а не только
  `tail`, иначе легко объявить проверку отсутствующей.
- **Пустой ответ поисковика — ещё не отсутствие файлов.** Встречалось: `Glob`
  по `**/*.ts` возвращал пусто там, где `ls` файлы видит. Прежде чем делать
  вывод «этого нет», перепроверить другим способом.

## Концы строк — политика репозитория, а не настройка машины

Отдельный пункт, потому что портит он не сборку, а **правки**: на машине с
`core.autocrlf=true` рабочее дерево окажется в CRLF, и любая замена
многострочного фрагмента, ищущая по одному лишь `\n`, не найдёт ничего —
молча, без ошибки. Инструмент отчитается «готово», а файл останется прежним.

Лечится одним файлом в корне, до первого коммита:

```gitattributes
# Line endings are repository policy, not a per-machine setting: LF in the
# repository and in the working tree, whatever core.autocrlf happens to be.
* text=auto eol=lf

# Binary assets must never be touched.
*.png binary
*.jpg binary
*.jpeg binary
*.webp binary
*.avif binary
*.woff binary
*.woff2 binary
```

Заведённый позже, он не перепишет уже лежащие файлы сам: их придётся
переиндексировать. Отсюда «до первого коммита», а не «когда попадётся».

## Как посадить в новый проект

1. Создать в корне проекта папку `.claude/`.
2. Скопировать `settings.template.json` как `.claude/settings.json`.
3. Сверить пути в записях с проектом: если база знаний лежит не в `.context/`,
   поправить строку `node .context/graph.mjs *`; если менеджер пакетов не npm —
   заменить команды проверок на свои из `CLAUDE.md`.
4. Положить в корень `.gitattributes` по образцу выше — **до первого коммита**.
5. Проверить на месте: один `npm test` и один поиск по репозиторию. Всплыло
   подтверждение — сначала посмотреть, есть ли команда в списке. **Нет —
   добавить; есть — списком это не лечится**, и дожимать его бесполезно:
   так уже было и с `grep`, и с `head`, каждый из которых в списке стоял.
   Лечится другим — не тем инструментом: поиск идёт инструментом `Grep`, а
   вызов оболочки упрощается до одной команды.

Экран `/permissions` показывает, какое правило сработало. Из сессии он не виден,
поэтому смотреть его — работа человека, а не агента.
